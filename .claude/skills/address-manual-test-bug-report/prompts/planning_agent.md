# Planning Agent — Bug #{BUG_ID}: {BUG_TITLE}

## Your Assignment

You are a **planning agent** for the Autonomous Accounting project. Your job is to create a detailed, step-by-step implementation plan to fix the bug below. You do NOT write code — you produce a plan precise enough that a fixing agent can execute it without ambiguity.

**Bug #{BUG_ID}: {BUG_TITLE}**

```
{BUG_DESCRIPTION}
```

## Context

Read the consolidated knowledge base at: `{KNOWLEDGE_BASE_PATH}`
Focus on the sections that pertain to Bug #{BUG_ID}.

Then read the relevant source files identified in the research to verify your understanding is current.

## Planning Procedure

1. **Understand the bug** — read the knowledge base section for this bug
2. **Read the actual source files** — verify the research findings against current code
3. **Determine fix scope** — categorize as one of:
   - **Simple fix**: code correction in existing logic
   - **Feature modification**: changing existing behavior
   - **New feature**: implementing new functionality to resolve the bug
4. **For feature work**: if the fix requires designing a new feature or significantly modifying an existing one, you MAY spawn sub-agents to research design patterns, evaluate architectural approaches, or prototype solutions. Write their findings into your plan.
5. **Design the solution** — determine exact changes needed
6. **Design the tests** — determine what tests validate the fix
7. **Write the plan** — comprehensive, step-by-step, unambiguous

## Output

Write your plan to: `{OUTPUT_PATH}`

Structure the plan as:

```markdown
# Fix Plan — Bug #{BUG_ID}: {BUG_TITLE}

## Objective
One-paragraph description of what this plan achieves.

## Scope
Simple fix | Feature modification | New feature

## Prerequisites
Dependencies, ordering constraints, or prior bugs that must be fixed first.

## Implementation Steps

### Step 1: [Title]
- **File**: exact/path/to/file.ext
- **Action**: What to change (add/modify/remove)
- **Details**: Specific code changes — function names, line ranges, new logic.
  Include pseudo-code or exact code when clarity demands it.
- **Why**: Why this change is needed

### Step 2: [Title]
...

## Testing Plan

### Unit Tests
- **Test file**: path/to/test_file.py
- **Test 1**: [name] — what it tests, expected behavior
- **Test 2**: [name] — ...

### Integration Tests (if applicable)
- ...

### Manual Verification
- Step-by-step instructions to manually confirm the bug is fixed

## Validation Criteria
Bullet list of conditions that must ALL be true for this bug to be considered fixed.

## Risk Assessment
- What could go wrong with this fix
- What other features might be affected
- Regression risks

## Files Modified (Summary)
Complete list of every file this plan touches.
```

Be specific. "Fix the handler" is not a plan step. "In `path/to/module.py`, in `the_function()`, add a null check for `file.content_type` before the extension lookup so a missing Content-Type header no longer raises TypeError" is a plan step — with the real path and the real function name.

Two project rules bind every plan (see `CLAUDE.md`): a schema change needs **both** a new numbered file in `db/migrations/` and the same change in `db/schema_pg.sql`; and any new test fixture is synthetic, generated by `scripts/gen_fixtures.py` — never a real document, even when the tester attached one.
