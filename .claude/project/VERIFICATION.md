# Verification — what counts as proof

## The standard

A claim that something works for a user is only as good as the evidence that a user could do it.
That evidence is a real browser driving the running app and showing the result. Not curl, not a
backend import, not a DB query, not a hand-shaped payload, not "the unit test passes."

This is not pedantry about tooling. Mocks and invented fixtures check the contract shape their
author imagined; the bugs that reach users are the ones where the real shape differs — a
serialization difference, an auth boundary, a frontend/backend naming mismatch. A suite that only
ever sees shapes we invented systematically misses exactly that class.

So: bug fixes, feature checks and end-to-end gates are driven through the app as a user, and
verified by what the UI shows. The unit suite (`pytest`) proves the engine's arithmetic and rules;
it does not prove a feature is reachable.

## Where to point the browser

The backend serves the built SPA and `/api/*` from one origin, `http://localhost:8080` by default
(`PORT`, `BASE_URL`). Use that rather than the Vite dev server (`:5174`) when the claim is "this
works for a user": the production bundle, the Content-Security-Policy and the same-origin cookie
and token handling are all part of what a real install serves, and each can break something that
works under the dev proxy. Rebuild `web/dist` first if frontend files changed — a running server
keeps serving the bundle and the Python code it started with.

If nothing answers, the stack is not running; `GET /health` says which of database, storage and
the LLM endpoint is the problem once it is.

## Accounts

Drive tests through a **throwaway account that holds only synthetic data** — create, edit, delete,
upload, mutate anything, no cleanup owed. Never point a test, a skill or an agent at an account
that holds someone's real books: the test suites delete things.

Registration is closed by default (`AUTH_ALLOW_SIGNUP=0`). A test that needs a fresh account sets
`AUTH_ALLOW_SIGNUP=1` in `.env`, restarts the server, signs up, and puts the flag back. With
`AUTH_AUTOCONFIRM=1` (the default) the account is usable the moment the form submits — no inbox,
no confirmation link.

Sign in with Google appears only when `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` are set. Do not
drive it from a test: it needs a real consent screen and it can only sign *in* to an account that
already exists, so it proves nothing password sign-in doesn't. Assert the button's presence or
absence, then sign in with the password.

Documents uploaded during verification come from `tests/fixtures/` (synthetic, generated by
`scripts/gen_fixtures.py`). Never a real receipt or statement — see *Never commit real financial
data* in `CLAUDE.md`; a real document dragged into a test run has a way of ending up in a
screenshot, a report or a fixture directory.

## Coverage

Test every surface a feature is actually reachable from, not just the first one. A slide-over that
appears on every statement tab gets exercised on at least two statements across two accounts; an
upload action gets exercised on both a matched and an ignored transaction.

When the UI is not enough on its own, the server log is the second source — uvicorn's output and
the files under `logs/`. There is no error-tracking service; the log on disk is it. What still
doesn't count is a fabricated payload or a mocked SDK call: a gate declared green on one is not
green.

## Tests, when we write them

- A test that passes while the feature is broken is worse than no test. If it can't fail, it isn't
  a test.
- The test is the verifier; the app is the subject. A failing test means fix the app — never edit
  a test to make it go green, and never stub out the real dependency to dodge a failure.
- A failure on your branch was caused by your change until you have shown otherwise by running the
  same test on `main`.
- The agent that wrote the code should not be the one that certifies it.
- `pytest.ini` carries a list of excluded legacy tests. It only ever shrinks.

## Engine accuracy

Extraction, reconciliation, categorization and ledger output are held to correctness over speed
and cost, always. Specifics that repeatedly matter:

- **LLM output is cross-verified.** Extracted numbers must reconcile deterministically — line items
  against totals, statement rows against the statement's own balances. An unchecked model number
  is a hallucination waiting to reach a tax filing.
- **Date mismatches are normal.** Invoice dates routinely precede bank clearing. One bank charge
  may cover several invoices; one invoice may be paid in installments. Treat these as the domain,
  not as errors.
- **Uncertain beats wrong.** Flag for human review rather than guess. A blank is better than a
  wrong number.
- **Never sum across currencies.** A total is per currency or it is not a total.
- **Every ledger entry links to its source document.** Auditability depends on it.
- **Fix the engine, not the scenario.** A miss found by a test or a manual run gets fixed in
  `core/` so the fix generalizes — not special-cased for the fixture that exposed it, and not
  tuned to one person's vendors. Editable tables belong in `config/*.yaml`; behaviour belongs in
  code.
